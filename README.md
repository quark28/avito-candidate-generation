# Avito - кандидатогенерация для поиска услуг

Для каждого поискового запроса решение отбирает до 50 объявлений из корпуса в 189 тыс. Метрика - Recall@50.

**Итог на Stepik: Recall@50 = 0.868** (валидация 0.9307, потолок пула кандидатов 0.9736)

Всё решение - один ноутбук `solution.ipynb`. Внешние API не используются, все модели open-source и работают локально.

## Как запустить

Ноутбук рассчитан на Kaggle с GPU (T4 или P100), время полного прогона около 3.5 часов.

1. Загрузить `train.parquet`, `benchmark_queries.parquet`, `benchmark_items.parquet` как Kaggle Dataset и подключить к ноутбуку.
2. Поправить `DATA_DIR` во второй ячейке на путь к датасету.
3. Включить GPU и интернет (нужен для скачивания модели эмбеддингов с Hugging Face).
4. Run All. Результат - `/kaggle/working/answer.csv`.

Для воспроизводимости зафиксированы seed (python, numpy, torch, LightGBM), детерминированный режим CUDA, число потоков LightGBM, ревизия модели эмбеддингов и все гиперпараметры. Порядок строк везде задаётся явной сортировкой. Версии библиотек - в `requirements.txt` (на Kaggle использовалась сборка torch 2.10.0+cu128).

Модель эмбеддингов: `intfloat/multilingual-e5-small`, ревизия `614241f622f53c4eeff9890bdc4f31cfecc418b3`.

SHA256 отправленного `answer.csv`: `9d10824618fbe9628bdc4dc65a636df8adb056c423233340abddb920f1bff0b7`

## EDA

Разведочный анализ - в `EDA.ipynb`. Главные выводы, на которых построено решение:

- 83% выборов сделаны в той же локации, что и поиск - отсюда два потока кандидатов.
- Категория поиска почти всегда совпадает с категорией объявления (53 несовпадения на 497 тыс.) - жёсткий фильтр.
- Фильтр "4 звезды и выше" - единственный вариант фильтра по рейтингу, соблюдается в 99% выборов.
- У 84% запросов ровно одно выбранное объявление, большинство объявлений выбраны один раз - популярность слабый сигнал.
- Только 9.6% объявлений корпуса встречаются в train - история выборов помогает мало, основной поиск по тексту.
- Повторные выборы одного объявления по запросу редки (15%), но растут с популярностью запроса до 47%.
- Запрос хорошо определяет микрокатегорию: например, 88% выборов по "автоподбор" в одной микрокатегории - признак `mc_share`.
- Поисков с доставкой всего 12 - признак не используется.

## Подход

Схема двухэтапная: сначала широкий пул кандидатов (~730 на запрос), потом ранжирование и топ-50.

**1. Жёсткие фильтры.**
- Категория объявления равна категории поиска. В train нарушений 53 из 497 тыс. Если категории запроса нет в корпусе (в бенчмарке 222 запроса с категорией 0), фильтр не применяется.
- Фильтр "Рейтинг пользователя 4 звезды и выше" соблюдается в 99% выборов. Объявления без рейтинга оставляем, среди выбранных по такому фильтру их 0.7%.

**2. Два потока по географии.** В train 83% выборов сделаны в той же локации, что и поиск. Поэтому кандидаты ищутся отдельно среди объявлений из локации запроса и среди остальных. Если у локации нет своих объявлений (так у 58 локаций-регионов), "местными" считаются локации, куда ходили люди из этой локации с похожими запросами - по истории train.

**3. Четыре источника в каждом потоке:**
- топ-250 по косинусу эмбеддингов запроса и заголовка;
- топ-100 BM25 по заголовку и параметрам;
- топ-100 BM25 по описанию;
- топ-100 по косинусу эмбеддингов запроса и описания.

BM25 со стеммингом Snowball ловит точные слова (марки, редкие термины), которые эмбеддинги пропускают. Для описания отдельный индекс, иначе длинный текст подавляет короткий заголовок.

**4. Ранжирование - LightGBM LambdaRank на 35 признаках:**
- скоры всех источников и их относительные версии - место кандидата в своём потоке и отставание от лучшего кандидата запроса;
- покрытие слов запроса в заголовке, параметрах, описании и точное вхождение фразы;
- `mc_share` - доля выборов в микрокатегории кандидата среди 50 самых похожих запросов истории;
- расстояние от центра города запроса, число объявлений в городе и в микрокатегории;
- рейтинг, отзывы, цена и их перцентили внутри пула, флаги контактов.

Самые важные признаки: место по BM25 описания, место по BM25 заголовка, место по эмбеддингу описания, расстояние, микрокатегория.

## Валидация

В бенчмарке все правильные ответы есть в корпусе. Для валидации берутся только запросы train, у которых все выбранные объявления тоже есть в корпусе (18 436 запросов). Из них 2500 - валидация, остальные - обучение ранкера. Строки этих запросов исключаются из истории, чтобы запрос не находил в ней собственный ответ.

Параметры LightGBM выбраны из 4 конфигураций по Recall@50 на валидации. Финальная модель обучена на обучающей части и валидации вместе, число деревьев фиксировано.

Все решения по поиску, признакам и параметрам принимались по этой валидации.

## Ошибки, найденные по ходу

- **Утечка в валидации.** Первая версия добавляла ответы из train в корпус. Ранкер научился отличать такие объявления по происхождению, и оценка на валидации оказалась сильно завышенной. Исправлено выбором запросов, чьи ответы уже в корпусе.
- **Запросы без категории.** В бенчмарке 9% запросов с категорией 0, которой нет у объявлений. Жёсткий фильтр оставлял для них ноль кандидатов, и они получали пустой ответ. В train таких запросов почти нет, поэтому на валидации это не было видно.
- **Регионы без объявлений.** У 17% запросов бенчмарка в локации поиска нет ни одного объявления - это регионы, а объявления привязаны к городам. Решено через историю: какие локации выбирали люди из этого региона.
- **Адрес в параметрах объявления** - шум для эмбеддингов, вырезается регуляркой до следующего известного ключа. Ключи собраны по данным, в 99.5% строк граница адреса находится на ключе.
- **Фильтр "Вид услуги"** соблюдается в 98.4% случаев. Нарушения - пограничные запросы вроде "аренда моющего пылесоса" (уборка или оборудование), фильтр, похоже, ставится автоматически. Жёстко по нему не режем.
- **Признаки кликов по объявлению** не используются: в валидации все ответы по построению встречаются в train, и такой признак завысил бы оценку.

## Черновые версии

В папке `experiments/` лежат промежуточные ноутбуки: `v1` - первая версия на эмбеддингах заголовка с валидацией, в которой была утечка, `v2` - валидация без утечки и первые признаки описания, `v4` - версия с потоками по описанию, из которой собран финальный ноутбук. Они оставлены для истории и воспроизводимость не гарантируют.

## Что можно улучшить

- Дообучить модель эмбеддингов на парах "запрос - выбранное объявление" из train.
- Разобраться с разницей между валидацией (0.931) и платформой (0.868). Вероятные причины: в валидацию не попадают запросы без категории, а её ответы - это объявления, которые есть и в train, то есть в среднем более "старые", чем ответы бенчмарка.
